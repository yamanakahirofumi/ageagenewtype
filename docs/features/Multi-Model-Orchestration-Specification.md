# マルチモデル・オーケストレーション機能仕様書

本ドキュメントでは、複数の小規模な生成AIモデル（例: 7B〜8Bクラスの軽量ローカルモデル）を協調・連携させることで、大規模モデル（フロンティアモデル）に匹敵する高品質・高精度なアウトプットを実現する「マルチモデル・オーケストレーション機能」の仕様提案を定義します。

---

## 1. 概要

### 背景と目的
ローカル環境で動作する 7B/8B パラメータクラスの軽量LLM（例: `llama3.2:3b`, `gemma2:9b`, `qwen2.5:7b`, `deepseek-r1:8b` など）は、応答スピードが速くメモリ消費が少ない反面、単一モデルでの複雑な推論、長文コード生成、あるいは広範なコンテキスト把握において大規模モデル（70B+ またはクラウドAPIモデル）に劣る場合があります。

本機能は、リソース制限のあるローカル環境において、**異なる強みを持つ複数の小規模モデルを役割分担・アンサンブル・反復評価によって組み合わせるオーケストレーション機構**を導入することで、「時間はかかっても高い正確性と品質を保証する」協調処理環境を提供することを目的とします。

### 基本方針
- **役割別専門化（Specialized Pipeline）**: 1つのモデルに全てを行わせるのではなく、「要件分解・設計」「コード記述」「レビュー・検証」「修正統合」などの各フェーズに適したモデルを割り当てます。
- **多数決・アンサンブル合意形成（Consensus & Ensemble）**: クリティカルな判断や複雑なロジック設計において、複数の異なる小規模モデル（例: `qwen2.5` と `gemma2` と `llama3.2`）に並列で解答を出力させ、集計・統合モジュール（Aggregator）によって最も適した回答を選択・統合します。
- **評価・自己修復ルーティング（Iterative Refinement Loop）**: `Verify` ステップでの検証結果（コンパイルエラー、テスト失敗、規約違反）をフィードバックし、修正に特化したモデル（例: 推論特化モデル `deepseek-r1` など）へルーティングして繰り返し修正させます。
- **非同期・パイプライン実行**: 時間がかかるマルチモデル処理中も JavaFX メイン UI をフリーズさせず、各モデルの思考・出力プロセスを段階的に視覚化します。

## 2. アーキテクチャと連携パターン

マルチモデル・オーケストレーションは、以下の3つの主要な連携パターンを提供します。

### 2.1. 役割分担パイプライン（Sequential Task Pipeline）
複雑な開発タスクを段階的に分解し、各段階に最適な小規模モデルを順次投入します。

```
[ユーザー要求]
      │
      ▼
┌──────────────┐
│  要件・設計  │ ◄── 思考・設計が得意なモデル (例: DeepSeek-R1 / Qwen)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ コード生成  │ ◄── コード生成が得意なモデル (例: Qwen-Coder / CodeLlama)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ コードレビュー│ ◄── 静的解析・整合性評価が得意なモデル (例: Llama3)
└──────────────┘
```

### 2.2. アンサンブル合意形成（Majority Voting & Aggregation）
アルゴリズム選定や難解なバグ調査などの重要タスクにおいて、複数の小規模モデルに同じプロンプトを与え、その出力を比較・採択します。

1. **並列出力 (Parallel Generation)**: 2〜3つの選択されたモデルに対し並列でタスクを発行。
2. **比較評価 (Cross-Evaluation / Peer Review)**: 互いの出力を相互チェック、または統合モデル（Aggregator Model）がベストな部分を抽出・合体。
3. **最終結果出力**: 最も信頼性の高い単一結果をワークフローの次ステップへ引き継ぐ。

### 2.3. 反復評価・自己修復ルーティング（Iterative Repair Routing）
既存の「出力の後は必ず検証（Output-then-Verify）」原則と連携し、検証失敗時に単一モデルでのリトライではなく、問題の性質に応じたモデルへ修正を委託します。

- **構文・コンパイルエラー**: 軽量・高速モデルによる即時修正。
- **論理バグ・テスト失敗**: 推論能力の高い思考特化モデル（Reasoning Model）への切り替えとコンテキスト補強。

## 3. データ構造と設定仕様

マルチモデル・オーケストレーションの構成は、既存のワークフロー JSON 定義を拡張して記述します。

```json

  "id": "multi-model-source-creation",

  "orchestration_mode": "PIPELINE_AND_ENSEMBLE",
  "steps": [
    {
      "phase": 1,

      "phase": 3,
      "name": "コード生成",

  ]

```

## 4. 既存システムとの整合性と拡張点

### 4.1. ワークフローエンジン (`WorkflowService`) の拡張
- 従来は単一のアクティブモデルで全ステップを実行していましたが、ステップごとに定義された `assigned_model` または `ensemble_models` を動的に切り替えて Ollama API (`OllamaApiService`) を呼び出す機構を追加します。
- モデル未インストール時の自動フォールバック機能（デフォルトアクティブモデルの適用）を実装します。

### 4.2. サポートAI Capability との連携
- `ollama-status` Capability を活用し、ローカル環境で利用可能なモデルのリストとリソース状況（VRAM / メモリ割り当て）を事前に確認します。
- メモリ不足によるOllamaのクラッシュを防ぐため、モデル切り替え時のシリアライズ（順次ロード・アンロード）を制御します。

### 4.3. UI / UX 可視化
- チャット画面およびワークフロー進行ステータス表示において、**「現在どのモデルが思考・応答中か」**アイコンやモデル名タグを表示します。
- アンサンブル処理中には、各モデルの比較検討経過（Model A, Model B の提案と統合理由）を折りたたみ可能なアコーディオンパネルで表示します。

## 5. 期待される効果と運用メリット

1. **高精度化（Quality Boosting）**: 単一の7Bモデルでは見落としがちなエッジケースや設計不整合を、複数モデルの相互検証（Peer Review）によって劇的に削減します。
2. **リソース効率化**: 70B級の大規模モデルを実行できない一般的なPC環境（VRAM 8GB〜16GB程度）でも、7B〜8Bクラスのモデルを順次入れ替えて実行することで、同等レベルの成果物をローカル完結で得られます。
3. **障害耐性向上**: 特定の小規模モデルがハルシネーションや不適切な出力を起こした場合でも、検証モデルやアンサンブル合意によって自動的に修正ループが機能します。
