# マルチモデル・オーケストレーション機能仕様書

本ドキュメントでは、複数の小規模な生成AIモデル（例: 7B〜8Bクラスの軽量ローカルモデル）を協調・連携させることで、時間はかかるものの、大規模モデル（フロンティアモデル）に匹敵する高品質・高精度なアウトプットを実現する「マルチモデル・オーケストレーション機能」の仕様提案を定義します。

---

## 1. 概要

### 背景と目的
ローカル環境で動作する 7B/8B パラメータクラスの軽量LLM（例: `llama3.2:3b`, `gemma2:9b`, `qwen2.5:7b`, `deepseek-r1:8b` など）は、応答スピードが速くメモリ消費が少ない反面、単一モデルでの複雑な推論、長文コード生成、あるいは広範なコンテキスト把握において大規模モデル（70B+ またはクラウドAPIモデル）に劣る場合があります。

本機能は、リソース制限のあるローカル環境において、**異なる強みを持つ複数の小規模モデルを役割分担・アンサンブル・反復評価によって組み合わせるオーケストレーション機構**を導入することで、「時間はかかっても高い正確性と品質を保証する」協調処理環境を提供することを目的とします。

### 基本方針
- **役割別専門化（Specialized Pipeline）**: 1つのモデルに全てを行わせるのではなく、「要件分解・設計」「コード記述」「レビュー・検証」「修正統合」などの各フェーズに適したモデルを割り当てます。
- **動的タスク分解（Dynamic Task Decomposition）**: 単一の大規模タスクを「設計方針作成」「モジュール分割」「アルゴリズム生成」「構文検証」といったマイクロタスクに自動分解し、それぞれの領域に強い軽量モデルへ順次委託します。
- **相互レビュー・自己修復・自己反省ルーティング（Peer Review & Self-Reflection Routing）**: 異なるモデルによる相互レビュー（Peer Review）に加え、同一または上位の専門モデルによる「自己反省（Self-Reflection）」評価を組み込み、指摘事項を理由・改善計画・修正コードに分類して繰り返し自律修正させます。
- **多数決・アンサンブル合意形成（Consensus & Ensemble）**: クリティカルな判断や複雑なロジック設計において、複数の異なる小規模モデルに並列で解答を出力させ、集計・統合モジュール（Aggregator）およびスコアリング構造化によって最も適した回答を選択・統合します。
- **リソース最適化・順次ロード制御（Serialized Model Swapping）**: VRAM/RAM リソースの限られたローカル環境に配慮し、Ollamaモデルの動的ロード・アンロードを順次制御（Serialization）して安全に実行します。
- **非同期・パイプライン実行**: 時間がかかるマルチモデル処理中も JavaFX メイン UI をフリーズさせず、各モデルの思考・出力プロセスを段階的に視覚化します。

## 2. アーキテクチャと連携パターン

マルチモデル・オーケストレーションは、以下の4つの主要な連携パターンを提供します。

### 2.1. 役割分担パイプライン（Sequential Task Pipeline）
複雑な開発タスクを段階的に分解し、各段階に最適な小規模モデルを順次投入します。

```
[ユーザー要求]
      │
      ▼
┌──────────────┐
│  要件・設計  │ ◄── 思考・設計が得意なモデル (例: DeepSeek-R1 / Qwen)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ コード生成  │ ◄── コード生成が得意なモデル (例: Qwen-Coder / CodeLlama)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ コードレビュー│ ◄── 静的解析・整合性評価が得意なモデル (例: Llama3)
└──────────────┘
```

### 2.2. 動的タスク分解と小規模モデル分散処理（Dynamic Task Decomposition & Dispatcher）
複雑で長文を要するリクエストを、タスク分解モデル（Decomposer Model）が依存関係を持つ複数のサブタスク（Sub-tasks）へ切り分けます。切り分けられたサブタスクは、専門分野を持つ各軽量モデルへ個別に投入されます。

1. **タスク分解 (Decomposition)**: 大まかな要求から機能定義書・API仕様・実装単位等のサブタスクを切り出し。
2. **分散アサイン (Sub-task Dispatch)**: サブタスクごとに最適モデル（例: UI設計→`gemma2`, ビジネスロジック→`qwen2.5-coder`）を割り当て。
3. **成果物結合 (Pipeline Integration)**: 最終出力ステップにて全成果物を単一のコード構造へバインド。

### 2.3. 相互レビュー・自己修復・自己反省ルーティング（Peer Review & Self-Reflection Routing）
作成された成果物に対し、別系統のモデルが「批評家（Critic）」としてレビューを行うとともに、生成モデル自身が「自己反省（Self-Reflection）」プロセスを通して自らの思考プロセスおよび出力を評価・検証します。

```
┌──────────────┐
│  コード生成  │ ◄── 生成モデル (例: Qwen-Coder)
└──────┬───────┘
       │ [出力コード]
       ▼
┌──────────────┐
│ 相互レビュー │ ◄── レビューモデル (例: Llama3 / Gemma2)
│ & 自己反省   │ ◄── 自己反省評価 (例: DeepSeek-R1 / Qwen)
└──────┬───────┘
       │ [指摘・自己反省レポート (CRITIQUE_REPORT)]
 ┌─────┴──────────────┐
 │ 問題あり？          │
 └─────┬──────────────┘
   YES │          │ NO
       ▼          ▼
┌──────────────┐ ┌──────────────┐
│ 計画・修正   │ │ 最終出力確定 │
│ (推論モデル) │ └──────────────┘
└──────────────┘ (例: DeepSeek-R1)
```

1. **自己反省（Self-Reflection）フェーズ**: 生成コードに対し、「要件を満たしているか」「境界条件のハンドリングが漏れていないか」「不要な重複・非効率な処理がないか」を問うプロンプトを発行し、明確な改善スコアと根拠を出力させます。
2. **ルーティング制御**:
   - **構文・コンパイルエラー**: 軽量・高速モデルによる即時修正。
   - **論理バグ・設計不整合**: 相互レビューおよび自己反省レポート（`CRITIQUE_REPORT`）を添えて推論特化モデル（`deepseek-r1` など）へ委託し、段階的な修正（Re-plan & Code Update）を実行します。

### 2.4. アンサンブル合意形成（Majority Voting & Aggregation）
アルゴリズム選定や難解なバグ調査などの重要タスクにおいて、複数の小規模モデルに同じプロンプトを与え、その出力を比較・採択・合成します。

1. **並列・順次出力 (Parallel/Sequential Generation)**: 2〜3つの選択されたモデルに対し順次/並列でタスクを発行。
2. **構造化採点・集計 (Structured Scoring & Aggregation)**: 集計モデル（Aggregator Model）が各モデルの出力を以下の基準で評価・採点（100点満点）します。
   - 正確性・仕様充足度 (Accuracy)
   - 可読性・保守性 (Readability)
   - 安全性・例外処理 (Robustness)
3. **ハイブリッド統合 (Hybrid Integration / Aggregation Strategy)**:
   - **MAJORITY_VOTE（多数決選択）**: 最高得点を獲得した単一出力をそのまま採択。
   - **BEST_PARTS_SYNTHESIS（最良部分合成）**: 各モデル出力の「長所（設計構造・例外ハンドリング・最適化アルゴリズム）」を切り出し、1つの矛盾のない統合成果物へ再構築。
4. **最終結果出力**: 採択理由または統合理由のサマリーを添えて、次ステップへ引き継ぐ。

## 4. 既存システムとの整合性と拡張点

### 4.1. ワークフローエンジン (`WorkflowService`) の拡張
- 従来は単一のアクティブモデルで全ステップを実行していましたが、ステップごとに定義された `assigned_model` または `ensemble_models` を動的に切り替えて Ollama API (`OllamaApiService`) を呼び出す機構を追加します。
- モデル未インストール時の自動フォールバック機能（デフォルトアクティブモデルの適用）を実装します。

### 4.2. サポートAI Capability およびリソース管理との連携
- `ollama-status` Capability を活用し、ローカル環境で利用可能なモデルのリストとリソース状況（VRAM / メモリ割り当て）を事前に確認します。
- メモリ不足によるOllamaのクラッシュを防ぐため、モデル切り替え時のシリアライズ（順次ロード・アンロード）を制御します。

### 4.3. UI / UX 可視化
- チャット画面およびワークフロー進行ステータス表示において、**「現在どのモデルが思考・応答中か」**アイコンやモデル名タグを表示します。
- アンサンブル処理中には、各モデルの比較検討経過（Model A, Model B の提案と統合理由）を折りたたみ可能なアコーディオンパネルで表示します。

## 5. 期待される効果と運用メリット

1. **高精度化（Quality Boosting）**: 単一の7Bモデルでは見落としがちなエッジケースや設計不整合を、複数モデルの相互検証（Peer Review）および相互アンサンブルによって劇的に削減します。
2. **リソース効率化**: 70B級の大規模モデルを実行できない一般的なPC環境（VRAM 8GB〜16GB程度）でも、7B〜8Bクラスのモデルを順次入れ替えて実行することで、同等レベルの成果物をローカル完結で得られます。
3. **障害耐性向上**: 特定の小規模モデルがハルシネーションや不適切な出力を起こした場合でも、検証モデルやアンサンブル合意によって自動的に修正ループが機能します。
