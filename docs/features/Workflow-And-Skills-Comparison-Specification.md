# ワークフローと生成AI Skills（能力）の比較仕様書

本ドキュメントでは、本アプリケーションにおける「ワークフロー」の考え方と、生成AIにおける「Skills（Capability / ツール呼び出し）」の考え方の概念、共通点、および違いについて定義・解説します。

---

## 1. 概要

### 背景と目的
生成AIを活用したシステム構築や開発支援において、単一のプロンプトによる一括生成だけでは、要件の考慮漏れ、誤った出力、あるいはハルシネーション（嘘の出力）といった品質のばらつきが発生しやすくなります。
本アプリでは、この課題に対処するために「**ワークフロー機能**」と「**サポートAI能力（Capability / Skills）**」の2つのメカニズムを採用しています。

両者はともに「AIの回答精度や実行確実性を高める」という目的を共有していますが、そのアプローチ、制御主体、および対象とする粒度には明確な違いがあります。本仕様書では、両概念を比較整理し、相互補完的な関係性を明らかにします。

## 2. 本アプリにおけるワークフローの概念

### 2.1 定義と目的
ワークフローとは、複雑な目標（例: ソースコードの新規作成やリファクタリング）を達成するために、定義された複数のステップ（タスク）を順次実行していく**「マクロなプロセスの構造化・制御メカニズム」**です。

### 2.2 主な特徴
- **Output-then-Verify（出力の後は必ず検証）原則**:
  成果物（設計書やコードなど）を出力するステップの直後には、必ずそれを客観的に評価・テストする検証ステップを配置します。
- **プロセス状態と実行制御**:
  ステップごとのフェーズ管理、検証失敗時の自動ループバック（前ステップへの差し戻し）、および段階的な情報収集ループ（`CLARIFICATION_REQUIRED`）を備えています。
- **透明性とガバナンス**:
  実行前に手順（ステップ構成）をユーザーに提示して承認を得る「Propose-then-Approve」モデルを採用し、ユーザーが進行状況や実行手順を完全に把握できます。

---

## 3. 生成AIにおけるSkills（Capability / ツール呼び出し）の概念

### 3.1 定義と目的
Skills（Capability / ツール呼び出し / Function Calling）とは、AIモデルが外部環境（ファイルシステム、Gitリポジトリ、セキュリティルール、OS環境情報など）と相互作用するために提供される**「ミクロな機能・道具（ツール）」**です。

### 3.2 主な特徴
- **単一機能のモジュール化**:
  `getId()` や `execute(argument)` のように、入出力が明確に規格化された単一のアクション（例: ファイル存在確認、Gitステータス取得、セキュリティチェック）を提供します。
- **モデル駆動による自律呼び出し**:
  LLM（生成AIモデル）が推論の過程で「外部情報が必要か」「どのアクションを実行すべきか」を自律的に判断し、必要に応じて呼び出します。
- **実行境界の拡張**:
  静的な学習データや与えられたプロンプトの枠を超え、最新の動的データやシステム状態にアクセスできるようにします。

---

## 4. ワークフローとSkillsの共通点

ワークフローとSkillsは、アプローチこそ異なるものの、設計思想やシステム上の役割において以下の共通点を持っています。

| 共通点 | 内容・説明 |
| :--- | :--- |
| **1. 信頼性と精度の向上** | 単発のプロンプト処理（一発勝負）によるハルシネーションや不確実性を排除し、結果の品質と再現性を極めて高く維持する。 |
| **2. モジュール性と高い拡張性** | 定期的な更新やカスタマイズが容易。ワークフローは JSON/YAML 定義、Skills は Java インターフェース（`SupportAICapability`）により独立して拡張可能。 |
| **3. コンテキストへの統合** | ステップの出力結果や Skill の実行戻り値は、後続のプロンプト文脈（コンテキスト）に統合され、AIの次なる思考や出力の材料となる。 |
| **4. AIによる動的判定・選択** | サポートAIやLLMがユーザーの依頼内容や対話文脈を分析し、最適なワークフローや実行すべき Skill を動的に選択・提案できる。 |

## 5. ワークフローとSkillsの違い（対比分析）

両者の根本的な違いは、「**プロセスの進行（How）**」を扱うか、「**手段・道具（What）**」を扱うかにあります。

### 5.1 比較対比表

| 比較項目 | ワークフロー (Workflow) | Skills (Capability / Tool) |
| :--- | :--- | :--- |
| **核心となる概念軸** | **「手順・プロセスの構造化」**（How） | **「機能・手段（ツール）の提供」**（What） |
| **制御の主体** | **システム / ワークフローエンジン**（決定論的または合意されたシーケンス） | **生成AIモデル自身**（推論過程における自律的ツール呼び出し） |
| **実行の粒度・スコープ** | **マクロ（巨視的）**：要件定義から検証・レビューに至る全体工程 | **ミクロ（微視的）**：単一のファイル参照、コマンド実行、データ取得など |
| **品質保証・検証構造** | **明示的な検証フェーズ**（Output-then-Verify による自動ループバック） | **個別実行結果の返却**（成功/失敗/エラー文字列のコンテキスト還元） |
| **ユーザーとの対話性** | **Propose-then-Approve**（提案と承認、確認質問ループによる進行制御） | **即時・自律的実行**（モデルが必要と判断した時点で内部実行） |
| **構成要素の単位** | **ステップ (Step)** の集合（順序付けされたタスク群） | **アトミックな関数 / 能力 (Atomic Capability)** |

### 5.2 詳細な相違点解説

#### 1. 制御主体と決定論的構造
- **ワークフロー**: システム側（ワークフローエンジン）が実行順序や状態遷移を管理します。失敗時には前のステップに自動的にループバックするなど、プロセス全体の決定論的な安全性を保障します。
- **Skills**: AIモデル自身が自律的に選択して呼び出します。どのタイミングでどの Skill を使うかは、LLMの推論能力に依存します。

#### 2. 品質保証の仕組み（検証の組み込み）
- **ワークフロー**: 「成果物出力」の後に必ず「検証ステップ」をペアで配置する「Output-then-Verify」原則が組み込まれており、エラーが発生した場合は合格するまで再実行を強制します。
- **Skills**: 各 Capability は単一のアクションを実行して結果を返すのみであり、その結果を受けてどう判断修正するかはモデル側のコンテキスト処理に委ねられます。

## 6. 相乗効果と連携パターン

本アプリでは、ワークフローと Skills は対立するものではなく、**相互に補完し合う関係**として設計されています。

```
[サポートAI (事前判定フェーズ)]
       │
       ├─► 【Skills (Capability) の利用】 (例: security-check, file-lookup)
       │     └─► ワークスペース状態やセキュリティの事前調査
       │
       ▼
[ワークフローの決定・承認]
       │
       ▼
[ワークフロー実行フェーズ]
       ├─► フェーズ1: 設計出力 ───► 検証 (AIセルフチェック)
       ├─► フェーズ2: コード生成 ───► 検証 (【Skills】による mvn test / ビルド実行)
       └─► フェーズ3: リファクタ ───► 検証 (【Skills】による 規約・静的解析)
```

### 6.1 主な連携パターン
1. **ワークフロー前処理での Skill 活用**:
   サポートAIは、ワークフローを提案する前の「事前判定フェーズ」において、`file-lookup` や `security-check` などの Skill を利用し、アクセス権限やファイルの有無を安全に事前確認します。
2. **検証ステップ内での Skill 実行**:
   ワークフローの「検証ステップ（Verify Task）」において、単体テストの実行（`mvn test`）や Git 状態の確認（`git-status`）などの Skill を呼び出すことで、プログラムによる客観的で厳格な自動検証を実現します。
3. **Skill によるワークフロー情報の照会**:
   `list-workflows` Capability のように、現在システムに存在するワークフロー一覧を取得する Skill を通じて、メタ情報へのアクセスを提供します。

### 6.2 まとめ
- **Skills（能力）** は、AIが外部世界に働きかけるための「**腕や道具**」です。
- **ワークフロー（手順）** は、目的を正しく達成するための「**設計図や進行ガイドライン**」です。
- 両者を組み合わせることで、「**適切な道具（Skills）を使いながら、正しい手順と厳格な検証（Workflow）に沿って高品質な成果物を生み出す**」ことが可能となります。
