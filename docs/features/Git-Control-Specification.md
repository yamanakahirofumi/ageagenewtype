# Git操作GUI仕様書

本ドキュメントでは、IDE 風デスクトップアプリケーションに統合される Git 操作 GUI 機能の仕様を定義します。開発者がコマンドラインを使用せずに、アプリケーション上で安全かつ直感的にバージョン管理を行えるようにすることを目的とします。

## 1. 概要

### 背景と目的
本アプリケーションは、ローカル LLM (Ollama) を利用した AI エージェント連携機能とテキスト/コードエディタを統合した環境を提供します。ソースコードやドキュメントを編集する中で、外部ツール（ターミナル等）に切り替えることなく、シームレスに Git 操作（変更のコミット、ブランチ切り替え、リモート同期など）を行えるようにすることで、開発・執筆の生産性を最大化します。

### 基本設計方針
- **ノンブロッキングUI (Non-blocking UI)**: ネットワーク通信が発生する処理（`fetch`, `pull`, `push` 等）や、重い入出力処理はすべてバックグラウンドスレッドで非同期に実行し、JavaFX のメイン GUI スレッドをフリーズさせません。
- **直感的なリポジトリ状態可視化**: 現在選択されているワークスペースが Git 管理下にあるかどうかを自動判定し、状態に応じた適切な UI（未初期化時の `init` 案内、ブランチ名、変更ファイル一覧など）を表示します。
- **安全第一のエラーハンドリング**: 競合（Conflict）や認証エラーなどの例外発生時、プロセスの強制終了やデータの破損を防ぎ、ユーザーに対して安全な解決策（競合箇所の明示、認証情報の入力等）を分かりやすく提示します。

## 2. GUI の配置と画面構成

Git GUI 機能は、既存の3分割 `SplitPane` レイアウトを崩さずに統合するため、以下の2つのインターフェースをサポートします。

### ① サイドバー「Git パネル」
画面左側の「ファイルツリー部」とタブ形式で切り替え、またはアコーディオン形式で併置される専用の **「Git パネル (Git Operations Pane)」** を提供します。

```
+------------------------------------+
| [File Tree] [ Git ]                | <-- タブ切り替え
+------------------------------------+
| Branch: [ feature/ai-chat     ][v] | <-- ブランチ選択・作成
| Sync: [ Fetch ] [ Pull ] [ Push ]  | <-- リモート同期ボタン
+------------------------------------+
| 変更されたファイル (Staged/Unstaged) |
| [ ] [Add]  src/Main.java           | <-- チェックボックスでStage/Unstage
| [x] [Mod]  docs/spec.md            |
+------------------------------------+
| コミットメッセージ入力                  |
| [ Implement Git checkout feature ] |
|                                    |
| [ Commit (Ctrl+Enter) ]            | <-- コミット実行ボタン
+------------------------------------+
```

### ② ステータスバー「Git ウィジェット」
画面最下部のステータスバーの左端に、現在の Git 状態を常時表示する簡易ウィジェットを配置します。

- **表示内容**:
  - 現在のブランチ名（例：`🌿 feature/ai-chat`）
  - リモートとの同期状態（例：`↑2 ↓1` - ローカルが2コミット先行、リモートから1コミット未取り込み）
  - リポジトリ未初期化時は `⚠️ No Git Repo` と表示。
- **クイックアクション**:
  - ウィジェットをクリックすることで、ブランチ一覧ダイアログをポップアップ表示し、その場でブランチの切り替えや新規作成を行えます。

## 3. Git 操作（コマンド）の GUI 仕様

本機能が提供するコアとなる Git 操作について、それぞれの GUI 表現と詳細な動作仕様を定義します。

### 3.1. `init` (リポジトリ初期化)
ワークスペース（作業ディレクトリ）が Git 管理されていない場合の初期化処理です。

- **トリガー条件**:
  - ワークスペースとして指定されたフォルダ直下に `.git` ディレクトリが存在しない場合。
- **GUI 表現**:
  - ファイルツリー部および Git パネルに **「Git リポジトリが検出されませんでした」** というプレースホルダー表示。
  - 中央に **[ Git リポジトリを初期化 (git init) ]** ボタンを表示。
- **動作フロー**:
  1. ユーザーが初期化ボタンをクリック。
  2. バックグラウンドで `git init` 相当の処理を実行。
  3. 処理完了後、自動的に現在のディレクトリを Git リポジトリとして認識。
  4. 初期ブランチ（通常は `main` または `master`）を作成し、ファイルツリーのファイル状態を「未追跡 (Untracked)」色（薄緑など）で更新。
  5. Git パネルを通常の操作画面へ遷移。

### 3.2. `fetch` (リモート追跡情報の更新)
リモートリポジトリの最新の変更内容（オブジェクトおよび参照情報）を取得します。

- **GUI 表現**:
  - Git パネル上部の **[ Fetch ]** ボタン。
- **動作フロー**:
  1. ボタンクリックにより非同期タスクを起動。ステータスバーおよびボタン上にローディング（インジケータ）を表示。
  2. リモート（デフォルトは `origin`）に対して `fetch` を実行。
  3. 完了後、ローカルとリモートのコミット差分（Ahead/Behind）を再計算し、ステータスバーの表示（例: `↑0 ↓3`）を更新。
  4. 完了通知を GUI 上部またはステータスバーに1.5秒間トースト表示。

### 3.3. `pull` (リモート変更の取り込み)
リモートブランチの変更を取得し、現在のローカルブランチに統合（マージ）します。

- **GUI 表現**:
  - Git パネル上部の **[ Pull ]** ボタン。
- **動作フロー**:
  1. ボタンクリック時、未コミットの変更がある場合は警告ダイアログ（「未コミットの変更があります。変更を退避(Stash)するか、コミットしてから実行してください」）を表示して処理を中断。
  2. バックグラウンドで `pull`（または `fetch` ＋ `merge`）を実行。
  3. **競合（Conflict）が発生しなかった場合**:
     - 変更が適用され、ファイルエディタを最新状態にリロード。ステータスバーを `↑0 ↓0` に更新。
  4. **競合（Conflict）が発生した場合**:
     - 後述の「4.2 競合発生時の対応仕様」に従い、競合解決インターフェースを起動。

### 3.4. `commit` (変更のコミット)
選択したファイル変更をローカルリポジトリに記録します。

- **GUI 表現**:
  - **変更ファイル一覧**: ワークスペース内の「修正 (Modified)」「削除 (Deleted)」「未追跡 (Untracked)」状態のファイルをリスト表示。各行にチェックボックスを用意。
    - チェックボックスを ON にすると **ステージングエリアに登録 (Stage / `git add`)** されます。
    - チェックボックスを OFF にすると **ステージングエリアから除外 (Unstage / `git reset`)** されます。
  - **コミットメッセージ入力エリア**: 複数行テキストエリア。
  - **[ コミット ] ボタン**: `Ctrl+Enter` ショートカットでも実行可能。
- **動作フロー**:
  1. ユーザーがコミット対象ファイルのチェックボックスを選択し、メッセージを入力。
  2. **[ コミット ]** ボタンをクリック。
  3. メッセージが空の場合は警告を表示し、処理を中断。
  4. バックグラウンドでステージングされたファイルのコミット処理を実行。
  5. コミット完了後、Git パネルの変更リストをクリア。ステータスバーの「Ahead (↑)」カウントをインクリメント。

### 3.5. `push` (リモートへの送信)
ローカルリポジトリのコミット内容をリモートリポジトリにアップロードします。

- **GUI 表現**:
  - Git パネル上部の **[ Push ]** ボタン。
- **動作フロー**:
  1. ボタンクリック時、現在のアクティブブランチに対応するリモート追跡ブランチ（Upstream）を確認。
  2. アップストリームが設定されていない場合、「プッシュ先のリモートブランチが設定されていません。`origin/[現在のブランチ名]` として新規作成しますか？」というダイアログを表示。
  3. バックグラウンドで `push` を実行。
  4. **認証エラー時**: 後述の認証ハンドリングを起動。
  5. 正常終了時、ステータスバーの「Ahead (↑)」カウントを `0` に更新し、成功メッセージを表示。

### 3.6. `checkout` (ブランチ・コミットの切り替え)
作業ブランチまたは指定したコミットへ作業ツリーを切り替えます。

- **GUI 表現**:
  - ブランチ選択ドロップダウン、またはステータスバーのブランチ表示クリックによる「ブランチ切り替えダイアログ」。
- **動作フロー**:
  1. ユーザーが一覧から切り替え対象のブランチ（または特定のコミットタグ）を選択。
  2. 作業ツリーに未コミットの変更がある場合、データの消失を防ぐためダイアログ（「未コミットの変更が衝突する可能性があります。変更を破棄するか、コミット・退避を行ってください」）を表示。
  3. バックグラウンドで切り替え処理を実行。
  4. ファイルツリーおよび現在オープンしているエディタの内容を自動リロード。

### 3.7. `branch作成` (新規ブランチの作成)
現在のコミット位置から新しいブランチを作成します。

- **GUI 表現**:
  - ブランチ選択ドロップダウン内、またはブランチ一覧ダイアログの右上にある **[＋ 新規ブランチ]** ボタン。
- **動作フロー**:
  1. ボタンクリックにより、小ダイアログ（「新規ブランチの作成」）をポップアップ表示。
  2. 入力項目：
     - **ブランチ名** (TextField): 必須。
     - **作成後にチェックアウトする** (CheckBox): デフォルトで ON。
  3. **ブランチ名バリデーション**:
     - 空白、タブ、全角文字の制限、および Git で使用不可能な記号（` `, `~`, `^`, `:`, `?`, `*`, `[`）の入力チェックを行い、エラー時はリアルタイムで赤字エラーを表示。
  4. **作成処理**:
     - 指定された名前でブランチを作成。チェックアウトが ON の場合は、即座に新規ブランチへ切り替え。
     - ステータスバーとブランチ一覧を最新状態に更新。

## 4. 特殊状態と例外処理

Git 操作ではネットワークやファイルの競合など、多くの例外シナリオが存在します。これらに対する詳細な制御仕様を定義します。

### 4.1. 認証が必要な場合（HTTPS / SSH）
`fetch`, `pull`, `push` 実行時に認証が求められた場合の処理です。

- **HTTPS 接続時の Personal Access Token (PAT) 認証**:
  - 認証エラー (`TransportException` など) を検知した場合、**「Git 資格情報の入力」** ダイアログをポップアップします。
  - ユーザーに「ユーザー名」および「パスワード / アクセストークン (PAT)」の入力を求めます。
  - 入力された資格情報は、安全なローカルセッション（またはOSのキーチェーン）に一時キャッシュし、次回の操作で再利用します。
- **SSH 接続時の鍵認証**:
  - デフォルトの `~/.ssh/id_rsa` や `id_ed25519` 等の SSH キーパスを自動探索します。
  - パスフレーズが必要な場合は、パスフレーズ入力用ダイアログを表示します。

### 4.2. 競合（Conflict）発生時の対応仕様
`pull` やマージ処理中にファイル競合が発生した場合のフローです。

```
+-------------------------------------------------------+
| ⚠️ ファイル競合が発生しました (Merge Conflict)        |
+-------------------------------------------------------+
| 競合しているファイル:                                 |
| > src/Main.java                                       |
|                                                       |
| [ エディタで競合を解決する ]   [ 今回のマージを中止 ] |
+-------------------------------------------------------+
```

- **状態の検知**:
  - 操作結果として競合（Conflict）を検知すると、ダイアログを表示して現在の状態を「マージ中 (MERGING)」としてマークします。
- **競合マークの表示**:
  - ファイルツリー上の競合ファイルを赤色の警告アイコンまたは「[Conflict]」接頭辞付きで強調表示します。
- **解決フロー**:
  1. 対象ファイルをエディタで開いた際、競合マーカー（`<<<<<<<`, `=======`, `>>>>>>>`）を分かりやすく強調。
  2. ユーザーが手動でファイルを修正し、保存。
  3. Git パネルで該当ファイルのチェックボックス（Stage）を ON にすることで「解決済み」とし、すべての競合がステージされたら、自動的にコミットメッセージ領域にデフォルトメッセージ（`Merge branch 'xxx' into yyy`）がセットされ、コミット可能になります。

## 5. 非同期処理とスレッド設計

JavaFX はシングルスレッド設計であるため、Git の入出力やネットワーク処理をメインスレッドで実行すると画面が完全にフリーズします。これを防止するため、以下のスレッド分離設計を厳守します。

### 5.1. JavaFX Concurrency ユーティリティの利用
- すべての Git コマンド処理は `javafx.concurrent.Task` または `javafx.concurrent.Service` を用いて、別スレッドの `ExecutorService` 上で実行します。
- 処理のフェーズごとに状態（`RUNNING`, `SUCCEEDED`, `FAILED`）を監視し、GUI にフィードバックします。

### 5.2. UI への安全な通知
- バックグラウンドスレッドから GUI コンポーネント（テキストエリア、リスト、ステータスバーなど）を変更する場合は、必ず `Platform.runLater(Runnable)` を経由してメインスレッドで処理を実行します。

| Git 操作処理 (Worker Thread) | | UI 描画処理 (JavaFX Application Thread) |
| :--- | :---: | :--- |
| `Git.pull().call()` 実行 | ──> | プログレスリングの表示開始 (`Platform.runLater`) |
| ネットワークからデータ取得・マージ | | (GUI は滑らかに動作、テキスト入力等が可能) |
| 処理成功で完了 | ──> | 完了通知トースト・エディタ内容リロード (`Platform.runLater`) |

## 6. セキュリティとエージェント連携

本アプリケーション特有の「AI エージェント機能」と Git 操作のセキュリティ境界について定義します。

### 6.1. エージェントによる Git 操作の制限
- [エージェント・セキュリティマネージャ仕様書](Agent-Security-Manager.md) に基づき、AI エージェントが自律的にコマンドライン経由で `git` を実行したり、`.git` ディレクトリ配下を直接操作したりする場合、セキュリティマネージャの `[program-execution]` および `[file-access]` の許可ルールに準拠している必要があります。
- **GUI からの人間による操作**:
  - 本仕様書で定義する GUI コントロール（ボタンクリック等）を通じた操作は、人間の明示的な意思決定（Human-in-the-Loop）であるため、セキュリティマネージャによる遮断制限は適用されず、常に実行可能です。

## 7. 技術選定方針 (参考)

GUI から Git 操作を Java で実行するにあたり、以下のいずれかの技術スタックを採用します。

- **候補A: JGit ライブラリ (推奨)**
  - Eclipse JGit (`org.eclipse.jgit`) を依存関係に追加。
  - Java API を通じてインプロセスで高速かつ高精度に Git 操作が可能。OS 依存の外部 `git` コマンドが未インストールでも動作する利点があります。
- **候補B: 外部プロセスの呼び出し (`ProcessBuilder`)**
  - システムにインストールされている `git` コマンドを実行。
  - 実装は単純ですが、OS 側のパス設定や `git` バージョンの違い、対話型プロンプト（認証など）のハンドリングが非常に複雑になるデメリットがあります。
