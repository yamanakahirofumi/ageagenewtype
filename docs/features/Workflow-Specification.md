# ワークフロー機能仕様書

本ドキュメントでは、AIによる処理結果を安定的かつ期待通りのもの（高品質・高精度）にするための「ワークフロー機能」の仕様を定義します。

---

## 1. 概要

### 背景と目的
生成AIを用いた開発支援や自動タスク実行において、AIに対して一度のプロンプトで複雑なタスクを全て完了させようとすると、考慮漏れ、誤った出力、あるいは要件の不整合といった問題（ハルシネーションや品質のばらつき）が生じる傾向があります。
本ワークフロー機能は、目的ごとに定義された複数のステップ（タスク）を順次実行し、さらに各出力ステップの直後に必ず検証ステップを挟むことで、AIの出力結果を極めて期待通りで信頼性の高いものにすることを目的とします。

### 基本方針
- **目的別のファイル定義**: AIに依頼するタスク（目的）の数だけ、個別のワークフローを定義・追加できます。
- **内蔵ワークフローの提供**: デフォルトで、最も頻繁に使用される「ソースコード作成（新規作成・修正）」のワークフローを内蔵します。
- **未知の依頼への動的生成**: 事前に定義されていない種類の依頼がユーザーからなされた場合、AIが最初に自らワークフロー（手順と検証方法）を立案・定義し、承認または合意形成の後にそのワークフローに沿ってタスクを進めます。
- **「出力の後は必ず検証」原則（Output-then-Verify）**: 何らかの成果物（設計書、コード、設定ファイルなど）を出力するタスクの後には、必ずそれを検証するタスク（静的解析、テスト実行、整合性確認、ピアレビューなど）を設定します。

## 2. ワークフローのデータ構造と定義フォーマット

ワークフロー定義は、拡張性・可読性に優れた JSON 形式または YAML 形式を採用します。以下は YAML 形式での基本モデル例です。

### ワークフロー定義ファイルの配置
ワークフロー定義ファイルは、ワークスペース配下の指定ディレクトリ、またはアプリケーションのシステムディレクトリに配置されます。
- システム内蔵ディレクトリ: `resources/workflows/`
- ユーザーカスタムディレクトリ: `${WORKSPACE_DIR}/.age/workflows/`

### ワークフローの構造定義（スキーマ例）

| フィールド名 | 型 | 説明 |
| :--- | :--- | :--- |
| `id` | String | ワークフローを一意に識別するID。（例: `source-code-creation`） |
| `name` | String | ワークフローの表示名。（例: `ソースコード作成・修正ワークフロー`） |
| `description` | String | ワークフローの目的や概要説明。 |
| `trigger_keywords` | List<String> | ユーザーの依頼内容からこのワークフローを自動選択するためのキーワード群。 |
| `steps` | List<Step> | ワークフローを構成するステップ（タスク）のシーケンス。 |

### ステップ（Step）の構造定義

| フィールド名 | 型 | 説明 |
| :--- | :--- | :--- |
| `phase` | Integer | ステップの実行順序（1から始まる連番）。 |
| `name` | String | ステップの名称（例: `要件定義`, `コード生成`, `単体テスト実行`）。 |
| `type` | String | `output`（出力タスク）または `verify`（検証タスク）のいずれか。 |
| `description` | String | このステップで実行すべき内容の指示（プロンプトに組み込む指示）。 |
| `verify_step_id` | String | `type: output` の場合に、直後に紐づける検証ステップのID。（必須項目） |

## 3. 内蔵ワークフロー：ソースコード作成

アプリケーションに最初から組み込まれている「ソースコード作成・修正」のための標準的なワークフロー定義です。

### ワークフロー全体の流れ
```
[ユーザーの依頼]
       │
       ▼
1. 要件整理・設計（出力） ───► 2. 設計整合性検証（検証）
       │
       ▼
3. コード生成（出力）     ───► 4. コンパイル・テスト実行検証（検証）
       │
       ▼
5. レビュー（出力）       ───► 6. 規約・安全基準検証（検証）
```

### 具体的なステップ定義内容

| フェーズ | ステップ名 | タイプ | 説明 / 指示内容 | 紐づく検証 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **要件・設計の定義** | `output` | ユーザーの要望から必要なクラス、メソッド、データ構造、入出力を設計し、設計ドキュメントを出力します。 | フェーズ2の検証 |
| **2** | **設計内容の整合性検証** | `verify` | 作成された設計が既存のアーキテクチャや制約事項と矛盾していないか、エッジケースが考慮されているかをAI自身がセルフチェックします。 | - |
| **3** | **ソースコードの生成・修正** | `output` | フェーズ1〜2で確定した設計に基づき、具体的なソースコードを生成または既存コードを修正してファイルに出力します。 | フェーズ4の検証 |
| **4** | **ビルドおよびテストによる動作検証** | `verify` | 実際にビルド（例: `mvn compile`）や単体テスト（例: `mvn test`）を実行、または疑似実行し、エラーがないことを確認します。 | - |
| **5** | **リファクタリングと修正提案** | `output` | 作成されたコードに対し、可読性向上、エラーハンドリングの強化、冗長なロジックの排除などの改善（リファクタリング）を行った結果を出力します。 | フェーズ6の検証 |
| **6** | **コーディング規約・セキュリティ検証** | `verify` | [コーディング規約](../tech/Coding-Convention.md)や[エージェント・セキュリティマネージャ仕様](../features/Agent-Security-Manager.md)に違反していないか、脆弱性がないかを静的に検証します。 | - |

## 4. 未定義の依頼内容に対する動的ワークフロー生成

あらかじめ定義されたワークフロー（内蔵またはカスタム定義ファイル）のいずれにもマッチしない新しい性質の依頼を受けた場合、システムは「アドホック（動的）ワークフロー生成」プロセスへと移行します。

### 動的生成プロセスフロー
1. **依頼内容の初期分析**
   - ユーザーから「〇〇をしてほしい」という未定義の指示が入力された際、AIが依頼のゴールと必要な中間成果物を分析します。
2. **ワークフロー案（ドラフト）の作成**
   - 依頼を完結させるために必要なステップ群を設計します。
   - この際、必ず**「成果物を出力するタスクの後には、それを評価・テストする検証タスクを対で定義する」**という原則を順守します。
3. **ユーザーへの提示と承認獲得**
   - 構築したワークフローのステップ一覧（出力と検証の構成）をチャットGUI上に分かりやすく提示します。
   - ユーザーから「この手順で進めてください（または修正指示）」の合意を得ることで、実行フェーズへ進みます。
4. **ワークフローに沿った実行と進捗管理**
   - 合意された動的ワークフローに基づき、ステップ1から順番にAIがタスクを実行し、各ステップの進捗をGUI上に可視化します。

## 5. 「出力の後は必ず検証」原則（Output-then-Verify）

本仕様の最も重要なルールであり、すべてのワークフローの基礎となる原則です。

### 原則の目的
AIは「一度に完璧なコードや文書を生成する」ことよりも、「生成した後に、客観的な基準でバグや不整合を見つけ出して修正する」プロセスのほうが圧倒的に高い品質を発揮します。この自己修復ループを強制するための仕組みが本原則です。

### 検証タスク（Verify Task）の要件とアプローチ
検証タスクでは、単に「コードが正しいか確認して」と依頼するだけではなく、以下のような具体的かつ客観的な検証手法を自動実行またはAIに強制します。

- **プログラムによる自動検証（推奨）**
  - コンパイル、静的コード解析ツール（Linter）、単体テスト（JUnit等）の実行と、その終了コードや出力結果のチェック。
- **多角的・客観的なセルフレビュー（AIによる検証）**
  - 「作成したコードの境界値テストケースを5つ挙げ、それぞれが期待通りに動くかトレースせよ」
  - 「[コーディング規約](../tech/Coding-Convention.md)のチェックリスト全項目（例: レコード型の使用、例外のラップ）について、適合しているか1項目ずつ確認せよ」
- **検証失敗時のハンドリング（ループバック処理）**
  - 検証タスクにて「失敗（エラー、不適合、バグ）」が検出された場合、システムは自動的に**直前の出力タスクへ差し戻し（ループバック）**を行います。
  - AIは検出されたエラーメッセージや指摘事項をコンテキストとして受け取り、修正コードを再出力し、再度検証タスクを通過させる必要があります。

## 6. サポートAIによるワークフロー判定と情報収集（事前判定フェーズ）

ユーザーが新しい会話（アクティブなワークフローがない状態）を開始した際、入力は直接メインAIモデルへ送信されるのではなく、まず**サポートAI（事前判定フェーズ）**によって処理されます。

### 事前判定フェーズの挙動
- **別セッションでの実行:** 判定セッションは、メインチャットやワークフロー実行セッションの会話コンテキストとは完全に隔離された「別セッション」として管理されます。
- **多言語対応（国際化）:** `Locale.getDefault()` に基づき、ユーザーのシステム言語（日本語または英語）を自動検出し、判定ルールやプロンプト指示を国際化して最適な言語で対話を行います。
- **不足情報の対話的収集（GATHERING）:** 入力内容が曖昧または不足している場合、判定AIは `"status": "GATHERING"` を返し、日本語（またはユーザー設定言語）で丁寧な質問を行います。この対話は、十分な情報が揃いワークフローが確定するまで繰り返されます。
- **ワークスペース・ファイルアクセスの判定とプリフェッチ:**
  - ユーザーの依頼がワークスペース内の特定ファイル（例: `pom.xml`, `Main.java`）の参照や変更を必要とするか判定します。
  - 必要と判定された場合、[セキュリティマネージャ（SecurityService）](Agent-Security-Manager.md)のアクセス権限を確認した上で、該当ファイルを安全に読み込み、事前コンテキストとして統合・添付します。これにより、ツール呼び出し（Tool-calling）機能を持たない軽量モデルでも、コンテキストを通じて正確にファイルを解析・実行できるようになります。

### ワークフローの提案とユーザー承認（Propose-then-Approve）
- 判定が確定（`"status": "DETERMINED"`）すると、サポートAIはそれらを自動実行するのではなく、チャット画面上に**ワークフロー提案（プレビュー）**として可視化します。
- ユーザーが「承認して開始（Approve & Start）」ボタンをクリックすることで初めてワークフロー（または標準チャット、ダイナミックワークフロー）が開始されます。

## 7. 手動選択オーバーライドとダイレクトクエリ

AIによる自動判定に加え、システムはユーザーに完全な制御権を提供します。

### UIでの手動選択
- チャット画面のモデル選択欄の下に「Workflow選択 ComboBox」を配置。
- ユーザーは以下からいつでも手動で実行モードを固定できます。
  1. **自動判定 (Auto):** サポートAIによる対話型事前判定を有効にします（デフォルト）。
  2. **標準チャット (Standard):** ワークフローを介さず、メインAIモデルと1往復の自由対話を行います。
  3. **ソースコード作成・修正ワークフロー:** 内蔵された定型クラス作成ワークフローを直接呼び出し、提案パネルを表示します。

### チャットによるワークフロー一覧照会
- チャット入力欄に「どんなワークフローがあるか」「list workflows」など、利用可能なワークフローについて質問するキーワードが含まれている場合、システムはAIモデルを呼び出さずにローカルで瞬時に照会をフック。
- 現在定義されているすべてのプリデファインド・ワークフロー（名称、概要、ステップ構成）の一覧をチャットUIに即座に表示します。

## 8. ワークフロー実行中の追加情報収集ループ

ワークフローの各ステップ（タスク）の実行中、AIモデルがタスクを完遂するために特定の仕様や詳細をユーザーに確認したい場合、システムは段階的な追加質問をサポートします。

- **質問検知とループバックの抑止:**
  - AIのステップ出力に `CLARIFICATION_REQUIRED` というマーカーが含まれている場合、システムは自動的な次のステップへの進行を一時停止します。
  - 画面にはAIからの追加の質問内容が表示され、入力待ち状態となります。
- **段階的な情報収集:**
  - ユーザーが回答を送信すると、その回答内容は現在のステップの文脈に追加され、**同じステップ**がもう一度再実行されます。
  - 十分な回答情報が蓄積され、`CLARIFICATION_REQUIRED` が出力されなくなるまで、同じフェーズに留まったまま対話を繰り返すことができます。
