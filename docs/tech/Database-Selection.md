# データベース選定方針

本アプリケーションでは、生成AIの対話履歴やプロンプト設定をローカル環境で効率的に管理し、将来的なデータ構造の変更やクエリの複雑化に対応するため、ファイルベースのリレーショナルデータベース (RDB) を採用します。

## 1. データベース候補

以下の3つの主要なファイルベースRDBを候補として検討しました。

| 候補 | 特徴 | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **SQLite** | 世界で最も広く使われている軽量RDB。1つのファイルに全データを保存。 | 高い移植性、設定不要、読み込みが高速。多くのツールで閲覧可能。 | 並列書き込みに弱い（本アプリでは許容範囲）。データ型が柔軟すぎて厳密性に欠ける場合がある。 |
| **H2 Database** | Java製の軽量RDB。インメモリモードとファイルモードの両方をサポート。 | Javaとの親和性が非常に高い。高速。MySQL/PostgreSQL互換モードがある。 | SQLiteほど汎用的な閲覧ツールが多くない。Javaランタイムに依存。 |
| **Apache Derby** | Java製のピュアJava RDB。JDKに標準で含まれていた時期もある。 | 高い信頼性と標準準拠。Javaとの親和性。 | H2に比べるとパフォーマンスや機能面でやや劣る場面がある。 |

## 2. 選定結果：SQLite

本プロジェクトでは、**SQLite** を採用します。

### 選定理由
1. **汎用性とポータビリティ**: 生成AIの対話データやプロンプト履歴はユーザーにとって重要なデータであり、将来的に他のツール（Markdown, Python, 他のAIツール等）でデータを利用・移行したい場合に、SQLiteであれば標準的なツールで容易にアクセス可能です。
2. **フットプリント**: アプリケーション本体に含めるライブラリが軽量であり、リソース消費が抑えられます。
3. **メンテナンス性**: 生成AIのデータ管理（対話履歴、プロンプトテンプレート情報）は読み込みや蓄積が中心であり、SQLiteの特性と合致しています。

## 3. アクセス方式の検討

JavaからSQLiteへアクセスするために、以下のスタックを採用します。

- **Driver**: [sqlite-jdbc](https://github.com/xerial/sqlite-jdbc)
- **ORM / Data Access**:
    - **初期段階**: シンプルな **JDBC** または **Spring Data JDBC (風の薄いラッパー)**。
    - **拡張時**: **MyBatis** または **Hibernate** (JPA)。
    - *方針*: 対話・プロンプトデータはスキーマが比較的固定されるため、まずは `sqlite-jdbc` を直接、またはシンプルな Repository パターンを介して利用し、ボイラープレートを削減します。

## 4. データ保存場所

アプリケーションのデータディレクトリ（OSごとの標準的な場所、例：`~/.genai/data/` またはアプリ実行ディレクトリ内の `data/`）に `.db` ファイルとして保存します。
